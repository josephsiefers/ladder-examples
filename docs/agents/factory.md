# Software factory

GitHub Actions runs three tasks on this repo. The owner merges every PR by hand.

| Task | Trigger | What a run does | Next |
| --- | --- | --- | --- |
| Implementer (`.github/workflows/implement.yml`) | The owner adds `ready-for-agent` to a ticket | If a run already has the ticket, a PR is already open, or a blocker isn't closed, comments and stops. Otherwise builds the ticket on `agent/issue-<n>` to the Definition of done and opens a draft PR, adding the run's peak context and `Closes #<n>` to its body. If it can't, it comments on the ticket and labels it `ready-for-human`. | The PR starts the checks and a review |
| Automated review (`.github/workflows/review.yml`, which calls `review-pr.yml`) | A PR opens, or the owner adds `agent-review` | Runs the code-review skill against the tickets the PR closes, checking the PR body's claims against the diff. Posts a comment-only review and labels the PR `review-passed` or `review-failed`. A pass marks a draft PR ready. A failure on a PR labelled `agent-fix-tried` also adds `ready-for-human`. | A failure on an `agent/issue-*` PR starts a fix run. Otherwise nothing: the owner merges, or pushes fixes and adds `agent-review` |
| Fix (`.github/workflows/fix.yml`) | A `review` run completes (`workflow_run`). It goes on only for a run that succeeded, on this repo's `agent/issue-*` branch, with an open PR and a `fail` verdict; any other run is skipped without a comment | Refuses, with a comment, if a run is already working on the PR, the PR has had its fix attempt (`agent-fix-tried`, which also adds `ready-for-human`), or its head moved since the review (also `ready-for-human`). Otherwise labels the PR `agent-working` and `agent-fix-tried`, weighs each finding against the spec and fixes it on the PR branch, pushes fast-forward only, and appends an "Acting on the review" section to the PR body. A finding that needs the owner, or a refused push, becomes a comment and `ready-for-human`, and nothing is pushed. | A review of the new head, inside the same run. A second failure stops at `ready-for-human` |

The automated checks (`.github/workflows/checks.yml`) run on every PR, and branch protection requires them on `master`.

## Rules

- **Only the owner adds trigger labels** (`ready-for-agent`, `agent-review`). The factory's GitHub token is the owner's, so a workflow can't tell the owner from the factory. Runs only remove trigger labels, or add labels that start nothing: `agent-working`, `agent-fix-tried`, `ready-for-human`, `review-passed`, `review-failed`.
- **The review-to-fix chain is a `workflow_run`, not a label.** `fix.yml` starts when a `review` run completes, so no run needs to add a trigger label to start it. A `workflow_run` workflow runs from `master`'s copy of its file. Its re-review runs inside the fix run, through the same reusable `review-pr.yml`, so it doesn't start another fix. The brake is the one-attempt cap, `agent-fix-tried`, not GitHub's limit of three chained `workflow_run` levels. To allow another fix attempt, the owner removes `agent-fix-tried`; the next failed review then starts a fix run.
- **The runner that runs Claude never holds the factory's GitHub token.** Each workflow is split into jobs, and each job gets a fresh runner. The job that runs Claude has at most a read-only `GITHUB_TOKEN`, and it hands on only text files and a git bundle. The jobs that hold the token run code from `master` only, and never run anything from the Claude job's output. No step merges. This matters because GitHub-hosted runners give passwordless `sudo`: once untrusted code runs on a runner, every later step there is exposed.
- **The review reads the PR but runs nothing from it.** Its prompts, permissions and scripts come from `master` (except `review.yml` and the `review-pr.yml` it calls, which a `pull_request` run takes from the PR branch), and Claude ignores any `.claude/` settings the PR brings. So a change to `.github/factory/` only takes effect once it is merged.
- **A run reads only what the owner wrote** on a ticket: its body and the owner's comments. The repo is public, and anyone can comment.
- **Prompts and tool permissions** live in `.github/factory/` and in the `claude` flags of each workflow. A prompt or permission change is a factory change, and gets human review like any other.
- **A fix run acts on the PR's branch, at the commit the review read.** Its build job checks out the PR at the reviewed commit and runs Claude with `fix.md` and the implementer's tools, settings and context notice, all from `master`. It adds commits on top and never rewrites them: the publish job pushes without `--force`, so git refuses the push if the owner pushed in the meantime, and the owner's commits are untouched. It has no `ANTHROPIC_API_KEY`: a finding that needs a live eval is handed back.
- **The implementer runs in auto mode; the review runs on its allow list alone.** The fix runs like the implementer. In the implementer, a call the settings' allow and deny rules don't decide goes to a classifier model, which runs it or blocks it; it is never left waiting for approval. `WebSearch` and `WebFetch` are there for current docs. They are in the implementer's `--tools` but not on the allow list in `implement-settings.json`, so the classifier judges every call. The review runs in `dontAsk` mode: a call off its allow list is refused, so the allow list is what keeps it from running the PR's code. That list is the `git` reads and `ls` in `review-settings.json`, plus the shell commands Claude Code itself treats as read-only (`cat`, `head`, `grep`, `wc`, `sed -n`). A deny list can't do that job, since `bash -c`, `sh`, `env` and other runners each get around one. The review's Write is allowed only into its out directory, its `git` calls are denied `--output` (which writes a file), and it has no web tools. Each workflow passes `--tools` with only the tools its task uses, and the settings turn off the bundled skills the prompts don't use, to keep the starting context small.

## Context notice

The Definition of done caps a ticket at one session (~150k tokens of context), but an agent can't see its own context size. So the implementer's settings run `scripts/check-context.ts` as a hook after every tool call (`PostToolUse` and `PostToolUseFailure`). It reads the session transcript and takes the main thread's current context: input + cache-read + cache-creation tokens on the latest main-thread assistant message, with subagent messages (`isSidechain: true`) left out. That is the measure the workflow's peak-context line uses. Below 100k it adds nothing. Past each threshold it adds one notice to the agent's context, at most once per session:

- **~100k:** "Context is at Nk of ~150k. If the rest of the ticket won't fit, stop now and write `blocked.md`."
- **150k:** "Context is at Nk, over the ~150k budget. Stop now and write `blocked.md`."

A run that stops for the budget writes a short `blocked.md`: what it built, and what of the ticket remains. It spends no tokens proposing a split; the owner splits the remainder with `/to-tickets` in a fresh session. The run's commits are not pushed.

The check never breaks a run: a transcript or input it can't read means no notice, and it always exits 0. The hook runs it with `--once-per-session`, which records the notices given in `$TMPDIR/ladder-context-check/<session id>.json`. Run without the flag, as in the demo, it gives a due notice every time. It stays silent for tool calls inside a subagent (the hook input has `agent_id`). Claude Code writes a subagent's messages to their own file, `<session id>/subagents/agent-<id>.jsonl`, so the session file the hook reads holds only the main thread. Its fixtures (`scripts/fixtures/context/`) follow that session file, checked against live sessions. The session file differs from the workflow's `stream-json` output, where subagent messages are marked by `parent_tool_use_id` instead.

## Secrets

| Secret | Used for |
| --- | --- |
| `CLAUDE_CODE_OAUTH_TOKEN` | Claude Code, from `claude setup-token` |
| `FACTORY_GITHUB_TOKEN` | A fine-grained personal access token for this repo only: Contents, Issues and Pull requests read/write. No Workflows permission, so runs can't change `.github/workflows/`. It expires: rotate it before then. |
| `ANTHROPIC_API_KEY` | The app's live evals. The workflow writes it to `.envrc`, which Claude is denied reading. |

The Claude job does hold `CLAUDE_CODE_OAUTH_TOKEN` and, in the implementer, `ANTHROPIC_API_KEY`. The fix's Claude job holds only `CLAUDE_CODE_OAUTH_TOKEN`; its claim job's `GITHUB_TOKEN` gets `actions: read`, to download the review run's artifact. In the implementer, code Claude writes and runs (an npm script, a test) can read both. Denying Claude `.envrc` stops casual exposure, not a determined injection. The network is open, and the auto-mode classifier blocks sending secrets out, but it is a model's judgement, not a guarantee. The review runs no code and has no web tools; its one way out is the review text, which is posted on the PR. Treat both as keys you can revoke and replace; the GitHub token is the one kept out of reach.

Set them, the labels and branch protection with `scripts/setup-factory.sh`. To rotate one token, re-run it and press Enter through the stages you don't need.
